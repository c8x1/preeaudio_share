# 技术授课深度重审：不能以正确性与图形完整代替知识增量

审查对象：`hongmeng_audio_design_review/pages/P01.json` 至 `P21.json` 中的可见元素、讲稿、时长与页间关系。审查日期：2026-10-20。此次不继承任何旧 PASS；未修改页面。

快照说明：本报告的 P01 与 6452 字统计基于重审开始时的原版。审计过程中主作者已将 P01 改为 30 秒开场，另有 `P01_TEACHING_REVIEW.md` 对新版实际 PNG 与讲稿独立复审；原始问题保留作整改记录，不代表新版仍为 3 分钟。

## 总判定

当前材料比上一版更准确，但仍未达到“55 分钟技术分享”的内容密度。主讲 15 页讲稿合计 **6452 个非空白字符**，其中还包括大量边界声明、过渡与重复结论。字符数只用于暴露篇幅，不是口播计时。当前有内容支撑的紧凑讲授约 **24–32 分钟**，需实际试讲校准；即使放慢语速，也没有依据宣称已经具备 55 分钟有效教学内容。附录全部讲完可以增加时间，但有多处与正文重复，不能直接相加。

目前常用的 `建议 N 分钟，包含逐步读图、停顿与互动` 不构成授课时长依据。听众回答一个尚未教过的问题、依次念函数名、在图旁停顿，都不能计作新增技术内容。P1 的 3 分钟标签尤其明显：它只提出一个观察语义问题，随后 P3 再讲一次答案，应缩到 **30–45 秒**。

空洞感的主要原因并非每页字太少，而是许多页面只到“对象 A 调用对象 B / 状态 A 变状态 B”这一层，没有展示为何这样设计、关键条件如何改变结果、并发时什么会出错、旧设计怎样解决同一问题。正文中最值得展开的机制，又被放到附录或者压成页脚一句话。

全局视角也仍不平衡：策略层主要表现为 `UpdateSessionOperation` 和“选择目标”方框，缺少一次真实的策略决定及其输入、状态变化、向执行侧传播的结果。不能据此认为“整个音频底座”已经讲清楚。

建议将正文组织成三个可走通的技术案件：① Start 的受理、两级队列与首帧；② Pause / Start / 迟到完成事件的生命周期正确性；③ Move 的旧 PA 握手与新 Manager 接图。线程、Buffer、CAS、Pull 分别作为解释案件中具体设计选择的深入段落。P19、P20、P17 中真正能解释问题的内容应进入正文；版本与边界留给讲稿和附录。

## 逐页结论

以下时长是**当前可见内容与已写讲稿**的有效讲授估计，不包含未写出的拓展、重复读图和虚设互动。补充方案必须完成源码核验后才能写入页面，不能据建议先画出实现。

### P01 一次 Start，什么时候才算开始播放？——缩短，当前不支持 3 分钟

- 独有知识增量：调用、管理确认、设备提交是不同观察语义。
- 缺口：没有一个实际失败或延迟例子，也没有事件定义与观测点的具体关系。标题的“什么时候”没有通过时序回答；三个并列卡片是概念分类。
- 重复：P3 负责回答 STARTED / RUNNING 与设备执行的分叉；P14 再讨论控制确认与出声。P1 提前消费了两页的结论。
- 合理时长：**30–45 秒**。328 字讲稿应进一步裁剪，若照读全部约需更久，但那不增加知识点。
- 改法：保留一句业务问题和一个真实矛盾：Start 返回成功为何不能用作首帧测量终点。给出本次要追踪的 session 与三个操作，随即进入源码案件。若坚持 3 分钟，必须新增完整日志交错推演，这会与 P3 冲突，故不建议。

### P02 音频底座的对象与通信通道——压缩为后续图的导航

- 独有知识增量：控制与数据使用不同通信方式；服务内部仍有复制；对象不等于进程。
- 缺口：没有进程/线程边界、对象持有关系、具体回调连接点，故听众仍难定位后续图里的异步边。策略框只列职责，未体现真实决策。
- 重复：两级队列与 P3 重复；共享缓冲与 P8 重复；节点图与 P10 重复。
- 合理时长：**1.5–2 分钟**。
- 改法：保留为统一地图，标出 Client 进程、AudioServer 内对象、管理/设备执行上下文，给关键边写明 IPC、共享内存、callback、queue。不要再解释各页细节。策略详细案例应单列实证页，或将本页并入 Start 全图。

### P03 Start 如何穿过策略、服务与两级队列——主题有深度，现图未把深度画出

- 独有知识增量：HpaeManager 入队后，管理线程再向 RendererManager 入队；管理 STARTED 不等待设备级 lambda 完成。
- **图上缺失**：两条 Manager 生命线只有入队箭头；没有 queue 受理点、dequeue / HandleRequests、设备 lambda 的 `SetState / ConnectInputSession / SetSessionFade / EffectStart`。因此“两次异步”虽然在讲稿中正确陈述，听众不能从图上判断哪个函数返回、哪个线程尚未执行。
- 还缺：`WaitForDataConnection` 的条件及其等待对象，失败返回对后续 Start 的影响；状态回程与设备侧执行的分叉位置。
- 重复：P1、P4、P7、P14 都会再次说“回程不等于出声”。
- 合理时长：**2–2.5 分钟**；目前 3 分钟尚可慢讲，但信息支撑不充分。
- 改法：以一条真实 session 展开“两次入队、两次消费、一次状态回程”。使用明确的同步调用细线与异步入队符号，管理消费的 activation 内分出设备 enqueue 和 STARTED callback。设备消费框内列 3–4 个真实操作。用一个合法交错说明客户端已 RUNNING 时设备请求仍待消费；这是需要核验的“可能交错”，不画固定全局顺序。

### P04 PA Start 的同步返回与操作回调——与 P03 配对讲，而非另一遍状态语义

- 独有知识增量：`PaLockGuard` 保护 mainloop，`pa_stream_cork(0)` 提交异步操作；该版本回调未检查 success。
- 缺口：PA 异步泳道折叠过多，没有 `pa_operation` / 协议响应 / threaded mainloop 回调所在上下文；不能只靠 cork 名字解释锁的必要性与锁持有范围。
- 重复：同步返回、操作回调、声学完成的区别已经在 P1/P3。
- 合理时长：**2–2.5 分钟**。
- 改法：与 P03 共用相同观察语义，补一段短源码标注锁范围、提交点、返回点、callback；只展开经第三方 PA 核验的真实路径。解释旧模型为什么要通过 PA mainloop 串行进入其状态体系，新模型将修改放到何处。未检查 success 可作源码阅读提醒，不应代替核心技术价值。

### P05 PA 普通主输出双线程——有证据，但仍只是调用链

- 独有知识增量：`primary.dq` 是 render 到 HDI 写线程的交接；传递 chunk 引用而非必然复制 PCM。
- 缺口：为何有独立写线程、消息所有权何时转移、排队时生产者与消费者各持有什么；没有展示一个队列积压后如何影响输出的实例。
- 重复：P06 再画同一交接；P08 又用它解释 Buffer。
- 合理时长：**1.5–2 分钟**。
- 改法：与 P06 合并成同一横向时间轴。选两个 chunk A/B，按源码推演 post、get、写入、释放引用的先后；标明积压是可发生情形，不填虚构时长。若解释独立写线程的原始动机，需找到注释/历史依据，不能猜动机。

### P06 新旧交接收拢——结论页，不足以独立 3 分钟

- 独有知识增量：新普通输出沿 `HandleMsg → Process → OutputCluster → SinkOutput → RenderFrame` 连续调用，少一处已定位交接。
- 缺口：少交接后原来写线程的 HDI_START/STOP 等职责由何处承接；RenderFrame 阻塞会怎样影响同线程消息与供数。只有优势，没有设计约束。
- 重复：P05、P07、P15。
- 合理时长：**1–1.5 分钟**。
- 改法：合并 P05/P06，用同一业务单位和相同设备边界对照。补一个思考有答案的具体推演：本轮 RenderFrame 返回之前到达的 Pause 何时执行？答案必须落到 P07 的循环与实际调用返回边界，不能宣称线程合并没有代价。

### P07 消息与数据共用循环——需解释调度行为而非念伪流程

- 独有知识增量：条件变量谓词、HandleMsg 在 Process 前；Notify 仍持锁。
- 缺口：运行中与空闲时不同唤醒谓词的效果；处理期间新消息下一轮消费；停止、空队列与正在运行对等待的影响。当前图未展示这些状态。
- 重复：P03 说消费队列，P09 讲队列；“不是全无锁”重复很多页。
- 合理时长：**1.5–2 分钟**。
- 改法：给 3 个真实循环片段：空闲无消息、Start 到达、运行时 Pause 在 Process 中途到达。用时序说明何时读谓词、何时 HandleMsg；解释 `IsRunning()` 满足时不会等待固定 tick。若涉及线程 pacing，需继续核验实际 I/O 与调度，不能从 CV 直接推周期。

### P08 Buffer 减在哪——目前只有职责清单，缺可计算推演

- 独有知识增量：共享缓冲、Converter 已处理缓存、端口结果队列、SinkOutput 字节拼帧是不同库存。
- 缺口：没有一个真实帧长与格式组合，没有库存变化过程；观众不易理解为何三种缓存不能合并、为何反复 Pull。抗抖动能力仍只有定性边界。
- 重复：P16、P18，且这两页的细节更适合作为本页推演基础。
- 合理时长：**2–2.5 分钟**。
- 改法：用源码/设备配置得到的具体格式与 frameLen、renderSize 展示一轮 Pull/转换/累积表；或者明确标成“算例，非产品默认值”，逐步计算样本、声道、字节。解释哪处吸收应用供数波动，哪处只负责格式和块长适配。无需所有缓存都叫“抗抖动 Buffer”；抗抖动结论要单独实验。

### P09 CAS 发布与批次消费——命名了算法，没有教会算法

- 独有知识增量：生产者头插，消费者原子摘批，反向遍历恢复发布次序。
- **缺竞争推演**：没有 P1/P2 同读 head、一次 CAS 失败、重读后重试的具体状态；没有消费者摘批时第三个生产者到达后归属下一批的情况。所谓“以两个请求说明”只写在 pacing，既没入图，也没入讲稿。
- **缺 ABA 设计**：源码有 64 位 token、低 32 位 index / 高 32 位 flag，`IncRequestIndex()` 取出后增加高位。它们是代码级知识，当前完全遗漏。应演算一个节点回收重用后的 `(index, flag)` 如何变化，再谨慎说明其版本检测作用；不能未经证明宣称绝对消除所有 ABA，有限计数回绕与调用约束需明确。
- 还缺：空闲链与请求链如何互换节点；默认原子内存序/发布可见性；实际消费调用者是否单消费者的证据。不得仅凭类名下结论。
- 重复：P17 容量慢路径被正文页脚预告而未解释。
- 合理时长：**1.5–2 分钟**。真实新增竞争与 token 推演后才可能成为 4–6 分钟核心段。
- 改法：正文展示 4–6 步竞争表或分步图，另一页展示摘批/反向消费/节点回收。将 P17 资源耗尽作为同一算法的完整生命周期结尾。保留最少边界声明，将主要篇幅用于演算。

### P10 节点图与 Pull——职责图尚未解释执行机制

- 独有知识增量：每会话处理链、场景混音与输出簇的职责；Pull 反向请求、结果正向返回。
- 缺口：图中对象类型与实例数、多个输入如何混合、一个下游请求会触发几个上游节点、缓存有数据时哪些节点跳过。仅两种箭头不足以让新员工理解 demand-driven 执行。
- 重复：P18 真的展开 Pull 条件；P11 才证明局部扩展。
- 合理时长：**1.5–2 分钟**。
- 改法：将 P18 移入正文，以两个会话 A/B 到同一 sceneMixer 的真实连接举例，编号说明 SinkOutput 从下游发起一次请求如何递归抵达输入、结果如何合并。节点实例共享关系必须由 Manager 创建/映射代码确认，不能凭示意画共享。

### P11 会话音效插入——少数有具体失败语义的页，应深化

- 缺口：图只有旧连接和步骤，缺“成功后的新连接”；失败路径没有指向仍保持工作的旧边。48kHz 双声道限制只在讲稿中。

- 合理时长：**1.5–2 分钟**。

### P12 Pause / Stop——有状态名，尚无完整状态机的教学价值

- 独有知识增量：PAUSING/STOPPING 协调 Gain 淡出与断图；OnFadeDone 再次投递请求。
- **过时回调缺口**：图下方仅一句“已 RUNNING 则退出”，没有 `Pause → PAUSING → Start → RUNNING → late OnFadeDone` 的时间线；也未画检查发生在 OnFadeDone 调用时还是 lambda 被设备队列消费时。源码中保护在 lambda 执行体内，这个位置直接决定正确性，应明确。
- 还缺：直接终态旁路到底跳过哪些操作；Pause、Stop 共用部分与不同终态；判断仅看 RUNNING 能保护哪些交错，不能扩张为通用操作代次隔离。建议分析 Pause→Start→Pause 的复合交错，但未核验前只列待分析，不给结论。
- 重复：P19 的迟到 Drain 保护是更完整的案例，可联讲但区分层次与状态枚举。
- 合理时长：**2–2.5 分钟**。
- 改法：正常路径状态机单页；竞态时序单页。列事件、当前 state、queue、图连接四列，展示迟到回调保护前后本会发生的错误。补从 Gain 到 callback 的真实链，不能只把 `OnFadeDone` 当同步状态迁移标签。

- 重复：P09 页脚。

- 改法：给一次容量演算，并标出是否发生分配/锁/丢弃。代码级好问题：消费者已经把节点返还 free list，但其 lambda 尚在临时数组待执行，此时 usedRequestCount 不等于“尚未完成的业务请求数”。核验后画清计数语义，避免仅背容量常量。

### P18 A3 一次 Pull——比 P10 更接近真实机制，提前到正文

- 独有知识增量：队列为空才 DoProcess，计算后仍空返回 nullptr，InputPort 收集非空结果。
- 缺口：缺第二次 Pull 命中已有结果的对照，缺 Converter 多帧与 SinkOutput 拼帧关系。
- 重复：P08、P10。
- 合理时长：**1.5–2 分钟**。
- 改法：同一 OutputPort 连续两次请求，列 queue before / DoProcess? / queue after / returned frame；再将这个机制嵌进 P08 的拼帧算例。让听众能预测某一步会不会重新计算，才算教会。

### P19 A4 迟到 Drain——当前最接近有效技术授课的页，升正文

- 独有知识增量：一个可发生的交错、明确错误风险、状态 guard 与正确结果；整条因果链完整。
- 缺口：状态/队列的关键源码仍未以短摘录呈现；Drain timeout 到继续 Stop 的条件可再精确；去掉 guard 的错误结果可以用一条虚线分支体现。

- 合理时长：**2–3 分钟**。
- 改法：移到正文，增加一个 3–6 行 guard 摘录。强调这是某种合法交错与公共服务正确性，不当作自研独有创新。用它引出“异步设计的困难是生命周期一致性”，再讲 P12 的设备队列保护。

### P20 A5 新旧 Move——应升正文，但要从比较口号进入过程比较

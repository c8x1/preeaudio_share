# 逐页内容与技术名词解释

这份材料配合 15 页补充稿阅读。每页先说明图的含义，再解释该页术语。逐字口语稿另见 speaker_notes.md。

## 先把几层关系放清楚

OSS 是 Open Sound System。它在时间线里代表早期录放音设备接口路线。ALSA 同时包含内核音频体系和用户态库；PulseAudio、JACK、PipeWire 是更上层的音频服务或媒体处理框架。因此它们不是依次替换后前者就消失的同类产品。PreeAudio/HPAE 的对照范围是鸿蒙音频框架内的引擎组织，不能把它当成某个 Linux 服务的直接后继。

| 层次或职责 | 例子 | 主要问题 |

|---|---|---|

| 设备与内核访问 | OSS 接口、ALSA 内核驱动 | 怎样录放音、怎样与硬件交换数据 |

| 用户态设备库 | ALSA-lib | 上层怎样使用设备与缓冲 |

| 音频服务或媒体图 | PulseAudio、JACK、PipeWire | 多路音频、节点依赖、周期与设备共享 |

| 系统策略 | WirePlumber；鸿蒙侧 Policy/Service 的相应职责 | 声音应送到哪里，状态变化后怎样组织 |

| 系统引擎内部 | PreeAudio/HPAE 的 Manager、Node、Cluster | 处理职责、管线与生命周期怎样组合 |

这些层次用于理解职责，不是一张严格可互换的部署图。不同系统中的层可能交叠。

## 第 1 页：音频引擎的软件架构演进时间线

### 这一页在讲什么

时间线描述不同阶段的架构重点，并不是把所有项目排成逐一替代的版本序列。OSS/ALSA 更靠近设备访问与驱动，音频服务处于更上层，JACK/PulseAudio/PipeWire 体现不同侧重；PreeAudio 是鸿蒙音频框架内的处理引擎。

### 术语与例子

- **OSS**：Open Sound System，开放声音系统。一套起源较早的 Unix 音频接口及相关驱动体系。典型应用通过设备文件和 ioctl 设置采样格式、读写录放音数据。时间线主要讨论它作为设备接口的历史角色，不表示所有 OSS 实现都只有最简单的功能。

- **/dev/dsp**：早期 OSS 常见的 PCM 设备入口。路径看起来像文件，实际读写由驱动处理；写入的是约定格式的音频样本，通常需先把 MP3 等压缩文件解码。dsp 是历史设备命名，不表示应用直接给某颗 DSP 芯片写程序。

- **ALSA**：Advanced Linux Sound Architecture，高级 Linux 声音架构。包括 Linux 内核音频驱动体系和用户态库。它负责把上层读写与具体硬件连接起来；PulseAudio、JACK、PipeWire 都可以把它作为设备后端。

- **POSIX**：Portable Operating System Interface，可移植操作系统接口标准。规定进程、线程、文件等系统接口。它不是音频引擎，图中用它限定讨论的操作系统背景。

- **用户态**：普通应用和服务运行的环境，与内核态相对。用户态服务通过系统调用访问内核管理的设备。PulseAudio、PipeWire 服务主要运行在这里。

- **音频服务**：在应用与设备之间协调声音的软件进程或服务，例如管理多个播放流、音量、路由和设备切换。它常依赖底层驱动，并不取代声卡驱动。

## 第 2 页：演进中的四个软件架构变化

### 这一页在讲什么

四个变化分别是硬件抽象、多流共享、处理组合与动态控制。节点图只是表示方式，真正的架构差异还包括节点的组织尺度、运行线程、状态更新和调度方式。

### 术语与例子

- **驱动**：了解具体设备并把统一接口转换成硬件操作的软件。声卡驱动通常还处理硬件中断、DMA 与设备缓冲；不要与 PipeWire 调度图里的 Driver 混为一谈。

- **流**：按时间连续到达或输出的音频数据及其状态。例如浏览器的一路播放可对应一条播放流，具有格式、音量、缓冲和目标设备等属性。

- **混音**：把多路音频按时间对齐、调整增益后合成为输出样本。最简单可理解为对应样本相加，但实际还需处理削波、声道和格式差异。

- **数据流图**：用节点表示处理者、连线表示数据传递关系的结构。A→C 表示 C 消费 A 的结果；运行时还需决定依赖、周期、缓冲和唤醒方式，画出图不等于已经实现调度器。

- **Node**：节点，一项处理职责的承载者，如输入、重采样、混音或输出。不同框架对 Node 的粒度和执行方式不同，不能只凭同名断定实现相同。

- **Cluster**：处理簇，PreeAudio/HPAE 中组织相关处理节点的一种结构。可用来理解一段处理管线及其组合边界；具体包含哪些节点、如何触发，要看对应 Cluster 实现。

- **Manager**：管理器。HPAE 中相应 Manager 负责组织流、节点连接、状态和处理过程。它是软件职责名称，不等同于所有系统中的统一调度线程。

- **控制与数据**：控制包括创建设备、调整音量、建立连接等状态变更；数据处理是持续搬运和计算音频样本。区分职责有助于避免配置操作妨碍实时计算，但不意味着每个框架都严格分成两个固定线程。

## 第 3 页：PulseAudio：以流和设备组织音频服务

### 这一页在讲什么

PulseAudio 页展示两层并行关系：应用与服务是进程边界，主循环与实时 I/O 是线程分工。sink-input 是播放流，Sink 是输出端。图只展示常见播放方向，不是全部录放音与模块路径。

### 术语与例子

- **进程**：操作系统提供的程序运行和资源隔离单位，通常拥有自己的虚拟地址空间。两个客户端进程不能像同一进程内那样直接访问彼此普通变量。

- **线程**：进程内的执行单元，同一进程的线程共享大部分地址空间。主线程可以处理配置，实时线程持续处理音频；多线程也会引入同步与竞争。

- **libpulse**：PulseAudio 的客户端库。应用用它与服务通信、建立流和传输音频；它本身不是内核声卡驱动。

- **主循环**：不断等待并处理事件的循环，如客户端请求、设备变化、定时器事件。它关注服务状态和控制，通常不承担所有周期性音频计算。

- **实时线程**：目标是在约定时限内完成处理的线程。实时调度优先级可减少被普通任务耽误的概率，但不保证任何工作量都能按时完成。

- **I/O**：Input/Output，输入/输出。在音频图里指获取或交付数据；具体可涉及设备、缓冲或进程之间的数据交换。

- **sink-input**：PulseAudio 中接入 Sink 的播放流对象，例如某应用的一路播放。名称中的 input 是相对 Sink 而言，不要误解成麦克风录音输入。

- **Sink**：接收音频的目标对象，常对应输出路径或设备，也可为虚拟目标。PulseAudio 的 Sink 可以汇合多个 sink-input；PreeAudio 中同名输出概念的具体职责需按其源码理解。

- **共享内存**：让多个进程映射同一块底层存储。生产者写入后，消费者可读取同一份数据，减少通过 socket 反复复制样本的需要；仍需协商格式、所有权和读写时机。

- **消息队列**：把控制请求或状态变化排队传给另一执行方的机制。异步投递消息与音频数据跨周期交付是不同概念，不能因为类名含 async 就断定会增加一个音频周期。

- **后端**：把上层通用处理连接到具体实现的适配部分。例如 ALSA 后端负责对接 ALSA 设备；也可以存在其它平台或虚拟设备后端。

## 第 4 页：JACK：共享端口缓冲与依赖图调度

### 这一页在讲什么

JACK 将多个音频处理者组织成按周期协作的依赖图。端口连接决定数据依赖，但是否并行还取决于实现、处理器资源和运行状态。PreeAudio 的对比重点是引擎内部处理图及状态管理。

### 术语与例子

- **JACK**：JACK Audio Connection Kit，一个面向低延迟音频与应用互连的系统。应用注册音频端口和处理回调，按共同处理周期协作。JACK1 与 JACK2 的实现和调度能力存在差异。

- **端口**：节点或客户端的数据连接端点，例如一个音频输入或输出端口。这里通常是软件音频端点，不是网线插口，也不是 TCP 端口号。

- **libjack**：JACK 的客户端库，提供连接服务、注册端口和回调等接口。实时计算实际由应用回调参与完成，不能把全部计算理解为服务进程内执行。

- **回调**：把函数交给框架，在特定事件或处理时机由框架调用。音频 process 回调每次处理规定数量的帧，开发者需在时限内返回。

- **process(nframes)**：JACK 处理回调的常见写法。nframes 表示本次应处理多少采样帧；双声道 128 帧对应每声道 128 个样本，总共 256 个声道样本。

- **依赖**：一个任务开始前必须满足的条件。若 C 要同时读取 A、B 本周期结果，就要等 A、B 均完成；只有 A 完成还不能计算 C。

- **串行**：任务依次执行，同一时刻不利用多个执行资源处理这些任务。串行顺序仍须满足数据依赖。

- **并行**：多个任务同时在不同执行资源上运行。只有彼此独立且资源足够的任务才可能并行；更多核心不能缩短所有依赖链。

- **生命周期**：对象创建、配置、启动、暂停、停止、销毁等状态过程。音频设备切换时，管理这些过程与正确处理样本同样重要。

## 第 5 页：PipeWire：策略管理与媒体图执行分离

### 这一页在讲什么

PipeWire 的重点是会话策略、对象配置与实时图执行的分工。Driver 是图周期发起者，activation 是运行记录，eventfd 是唤醒机制。它们不是三种音频算法。

### 术语与例子

- **PipeWire**：把媒体处理组织为节点、端口和连接的框架，覆盖音频与视频场景。它提供图执行和对象机制，会话管理器负责大量系统策略。

- **WirePlumber**：PipeWire 的一种会话与策略管理器，监视对象和事件，执行设备选择、连接与路由等规则。它并非每个音频周期都替节点计算样本。

- **会话管理器**：根据系统状态和用户意图组织媒体对象的管理者。这里的会话不只是登录窗口或网络连接，还包含设备、应用流及其连接关系。

- **Driver**：本稿 PipeWire 调度部分指驱动图周期的节点，节奏可来自硬件事件或计时器。它决定何时启动处理周期，和内核声卡驱动处于不同抽象层。

- **activation**：PipeWire 节点执行所需的共享激活状态，包含依赖计数及运行状态等信息。它帮助跨进程节点协调何时可运行，不是媒体样本本身。

- **eventfd**：Linux 用文件描述符提供的轻量通知机制，可用于唤醒等待的线程。在 PipeWire 图里用于运行通知；音频样本通过另行准备的缓冲传递。

- **IPC**：Inter-Process Communication，进程间通信。用于不同进程之间交换配置、对象信息或数据；共享内存、socket、eventfd 在其中承担不同角色。

- **实时图**：需要按连续音频周期执行的处理图。控制层先准备连接和缓冲，运行时节点按依赖计算；实时图不表示每个节点都必然位于同一进程。

## 第 6 页：设计理念与软件架构的横向对比

### 这一页在讲什么

此表是架构重心的归纳，不是性能排行榜，也不是所有项目作者的设计目标原文。比较的对象范围不同，必须结合线程、时钟、缓冲、依赖与状态管理理解。

### 术语与例子

- **Source**：提供音频的源对象，常见是采集输入，也可以是虚拟源。与 Sink 方向相反；特定框架里还可能有设备监听源等扩展。

- **时钟**：决定音频数据推进速度与时刻的基准。设备可能各有时钟，存在微小速率偏差，因此需要缓冲、重采样或其它同步处理。

- **关键路径**：图中必须先后完成、总耗时最长的一条依赖路径，它限制理想情况下一个周期能多快完成。例如 A、B 并行后汇入 C、D，最短时间下界为 max(A,B)+C+D。

- **Policy**：策略职责，决定音频应怎样使用，例如目标设备、场景与路由规则。在本稿 HPAE 对照中指系统策略层职责，不代表每条规则都在引擎内部执行。

- **Service**：服务职责，对接系统请求、会话与运行管理，再与引擎协调。具体模块边界以所引用源码为准。

- **HPAE**：本稿 PreeAudio 对照所依据的鸿蒙音频引擎源码模块标识，常见于 HpaeNode、HpaeRendererManager 等类名。本文不为该缩写补造未经所引源码说明的英文展开式。

- **架构取舍**：为某个目标选择职责、执行与缓冲方式，同时接受代价。例如跨周期缓冲可减少同周期等待，但会增加交付延迟。不能只靠抽象名称给出性能排名。

## 第 7 页：素材参考：PulseAudio 的多级缓冲

### 这一页在讲什么

图中的多个缓冲跨越传输、流处理和设备三个边界。重采样属于信号处理，缓冲属于数据组织；二者相关但不能混为同一概念。缓冲容量、当前积压和端到端时延也不同。

### 术语与例子

- **Buffer**：缓冲区，临时保存待处理或待交付的数据。它可吸收生产与消费时间波动，但已经排队的数据会增加等待；容量上限与实际排队量不是一回事。

- **PCM**：Pulse Code Modulation，脉冲编码调制。这里主要指按采样率、声道和样本格式组织的数字音频样本，区别于 MP3/AAC 等压缩码流。PCM 不只意味着某一种固定整数位宽。

- **采样率**：每声道每秒记录或输出的采样帧数，单位 Hz。48 kHz 意味着每声道每秒 48000 个采样时刻，不等同于码率。

- **重采样**：把一种采样率的样本序列转换成另一种，例如 44.1 kHz→48 kHz。它要按新的采样时刻重建样本，不能简单改一个格式标签。

- **stream buffer**：流级缓冲，保存某条应用流的数据，协调应用提交与服务消费速度。各条流可以有不同的排队状态。

- **render queue**：渲染或输出准备阶段的队列，保存为输出准备的数据。它与每条输入流缓冲、硬件缓冲的职责不同，确切位置以所示 PulseAudio 版本为准。

- **device buffer**：设备或驱动输出路径使用的缓冲。声卡按硬件时钟持续消费，服务需及时补充；设备缓冲的排队数据也构成输出延迟。

- **端到端时延**：从选定起点到最终可听输出等终点的总耗时。包含采集、排队、处理、跨周期传递和设备输出等部分；比较时必须先说清测量边界。

## 第 8 页：JACK 附录：一个处理周期如何完成

### 这一页在讲什么

N/fs 给出音频块代表的时间。实时预算关注的是赶上交付时限，尤其是图的关键路径及调度开销。frame 是同一时刻的全部声道样本，不是整块 buffer。

### 术语与例子

- **采样帧**：同一采样时刻所有声道样本的集合。双声道一帧含左、右两个样本；128 帧不等于双声道合计 128 个样本。

- **样本**：某个声道在某个采样时刻的数值。样本位宽和格式决定如何存储它，比如 16 位整数或 32 位浮点。

- **声道**：独立的声音信号通道，如立体声的左声道和右声道。声道数量会影响每帧字节数和处理量。

- **处理周期**：音频系统一次处理一批帧的节奏。若每次处理 128 帧、采样率 48000 Hz，则名义周期为 128÷48000≈2.67 ms。

- **process(nframes)**：JACK 处理回调的常见写法。nframes 表示本次应处理多少采样帧；双声道 128 帧对应每声道 128 个样本，总共 256 个声道样本。

- **实时预算**：在下一次交付期限前可用的处理时间。2.67 ms 是相关整条依赖链共享的时限，不能给链上每个节点各分配 2.67 ms 后仍期望同周期完成。

- **阻塞**：线程因等待锁、磁盘、网络或其它事件而暂时不能继续执行。不可控的等待可能导致音频回调错过截止时间。

- **underrun / xrun**：underrun 指播放方需要样本时数据没有及时准备好；采集方来不及取走可发生 overrun。xrun 是这类缓冲/时限异常的统称，可能表现为断音或爆音。

## 第 9 页：JACK 附录：串行顺序与依赖驱动

### 这一页在讲什么

该算例的理想并行总耗时是 max(2,3)+2+1=6，串行总工作为8。关键路径描述依赖链的长度，不能把理想算例换算成产品加速比。无锁只按证据描述图访问机制。

### 术语与例子

- **关键路径**：图中必须先后完成、总耗时最长的一条依赖路径，它限制理想情况下一个周期能多快完成。例如 A、B 并行后汇入 C、D，最短时间下界为 max(A,B)+C+D。

- **依赖驱动**：前置工作完成后，使后继任务具备执行条件的组织方式。它允许独立分支并行，但不保证操作系统会立刻分配 CPU。

- **激活**：这里指使节点进入可运行流程或触发唤醒。须区分依赖已满足、通知已发送、线程实际获得 CPU 三个时刻。

- **工作核**：用于运行工作线程的 CPU 核心资源。教材算例假设两个执行资源，并未证明实际框架固定把每个客户端绑定一个物理核。

- **无锁**：在特定操作路径中不依赖常规互斥锁等待的设计。例如图访问的无锁机制不能外推成整个音频服务任意操作都无锁，也不自动等于没有其它等待。

- **同步开销**：为了协调执行产生的成本，包括通知、线程唤醒、调度和缓存一致性等。理想关键路径算例没有计算这些开销。

## 第 10 页：JACK 附录：同步与异步的交付取舍

### 这一页在讲什么

JACK2 的同步/异步是服务器级激活与交付方式。同步使用当期图结果，异步使用前一周期输出。它与串行/并行、API 阻塞/非阻塞都不是同一个分类维度。

### 术语与例子

- **同步 / 异步**：必须说明作用范围。JACK2 服务器模式讨论本周期处理与输出交付关系；PipeWire 异步 Link 讨论跨连接的周期隔离；异步控制消息仅说明请求与处理不必当场完成。三者不能互相替代。

- **流水线延迟**：把工作分到相邻周期后，数据经过额外阶段所产生的等待。可以提高不同阶段重叠运行的机会，但延迟增加不代表算法计算量减少。

- **截止时间**：某批音频最晚应完成并交付的时间。平均处理很快仍可能因偶发超时发生 xrun，所以实时系统也关心最坏情况与波动。

- **串行**：任务依次执行，同一时刻不利用多个执行资源处理这些任务。串行顺序仍须满足数据依赖。

- **并行**：多个任务同时在不同执行资源上运行。只有彼此独立且资源足够的任务才可能并行；更多核心不能缩短所有依赖链。

## 第 11 页：PipeWire 附录：会话策略如何改变运行图

### 这一页在讲什么

WirePlumber 不只负责连线，还负责设备和节点的准备、链接管理及元数据。上层管理图如何组织，实时层处理数据。图中的顺序是职责示意，不是固定调用时序。

### 术语与例子

- **会话管理器**：根据系统状态和用户意图组织媒体对象的管理者。这里的会话不只是登录窗口或网络连接，还包含设备、应用流及其连接关系。

- **WirePlumber**：PipeWire 的一种会话与策略管理器，监视对象和事件，执行设备选择、连接与路由等规则。它并非每个音频周期都替节点计算样本。

- **策略**：根据目标和当前状态作选择的规则，例如蓝牙耳机连上后是否切换输出、哪些流跟随默认设备。它决定组织意图，实时机制负责执行既定处理。

- **格式协商**：连接双方选择可接受的数据格式、采样率、声道布局等参数。如果双方不能直接匹配，可能需要适配节点或转换。

- **元数据**：描述对象与意图的信息，如默认目标、属性和关联状态；它不承载逐个 PCM 样本。不能把元数据更新等同于播放音频。

- **路由**：决定音频从哪里来、经过哪些处理、最终去哪里。例如把通话流送到耳机而不是扬声器。

- **设备配置**：设备工作方式的选择，如可用 profile、端口或录放音组合。选定后还需配置节点、端口与连接，设备出现不等于流已可播放。

## 第 12 页：PipeWire 附录：依赖计数决定节点何时运行

### 这一页在讲什么

pending 是剩余未满足依赖的计数。此页只显示 Driver 门控释放后的上游工作依赖，省略 Driver 的完整计数。pending 归零意味着满足图中的运行条件，真正执行仍需要线程获得调度。

### 术语与例子

- **Driver**：本稿 PipeWire 调度部分指驱动图周期的节点，节奏可来自硬件事件或计时器。它决定何时启动处理周期，和内核声卡驱动处于不同抽象层。

- **pending**：仍待满足的依赖计数。教学例中 C 等 A、B：2→1→0；零表示具备运行条件。实际 PipeWire 计数还涉及 Driver 等依赖，不能把图中简化数字逐字套到所有源码记录。

- **required**：节点一个周期所需的依赖数量，用于建立或重置等待条件。它是调度状态的一部分，不是需要多少字节音频数据。

- **activation**：PipeWire 节点执行所需的共享激活状态，包含依赖计数及运行状态等信息。它帮助跨进程节点协调何时可运行，不是媒体样本本身。

- **eventfd**：Linux 用文件描述符提供的轻量通知机制，可用于唤醒等待的线程。在 PipeWire 图里用于运行通知；音频样本通过另行准备的缓冲传递。

- **就绪**：依赖和运行条件已满足，任务可以被调度。就绪不表示已经开始执行，更不表示已经计算完成。

- **调度器**：决定可运行任务何时、在哪个执行资源上执行的机制。图调度决定依赖关系，操作系统线程调度仍影响实际获得 CPU 的时刻。

## 第 13 页：PipeWire 附录：跨进程的数据与唤醒协作

### 这一页在讲什么

跨进程处理依赖共享资源和同步通知。共享内存映射允许多个进程访问同一底层存储，但进程中的虚拟地址未必相同。eventfd 传通知，媒体缓冲传样本，主线程配置对象。

### 术语与例子

- **地址空间**：进程看到的虚拟内存地址范围。同一底层共享存储在两个进程里可以映射到不同虚拟地址，所以跨进程不能任意传递普通指针使用。

- **共享内存**：让多个进程映射同一块底层存储。生产者写入后，消费者可读取同一份数据，减少通过 socket 反复复制样本的需要；仍需协商格式、所有权和读写时机。

- **映射**：建立进程虚拟地址与底层存储的访问关系。两个进程分别映射同一共享内存对象，才可以各自在自己的地址空间访问它。

- **IPC**：Inter-Process Communication，进程间通信。用于不同进程之间交换配置、对象信息或数据；共享内存、socket、eventfd 在其中承担不同角色。

- **I/O 区**：PipeWire/SPA 交换处理状态与缓冲标识等信息的区域。它帮助说明当前应消费或提供哪份缓冲，不能一概等同于存放所有音频样本的媒体内存。

- **eventfd**：Linux 用文件描述符提供的轻量通知机制，可用于唤醒等待的线程。在 PipeWire 图里用于运行通知；音频样本通过另行准备的缓冲传递。

- **零拷贝**：在明确的数据路径中避免复制媒体内容。共享内存让某段传输有机会免复制，但重采样、混音、格式转换和设备交付仍可能读写新缓冲。

## 第 14 页：PipeWire 附录：异步 Link 的周期隔离

### 这一页在讲什么

PipeWire 异步 Link 的两个 I/O 槽位交替承担读写，使一般异步连接的消费者读取上一周期结果。作用范围是节点/连接，不等同于 JACK2 的服务器级激活，也不等同于控制消息的异步排队。

### 术语与例子

- **Link**：PipeWire 中连接端口的对象，表达数据流关系，并涉及格式、缓冲与运行状态。它不是网页超链接。

- **异步 Link**：关联异步节点的跨周期交付连接。按所引调度文档，一般异步连接使接收方使用上一周期数据，每条增加一个图周期；Driver 输出等特殊分支需单独看。

- **双槽缓冲**：本页指交替使用两个 I/O 交接槽：周期 c 输出选 (c+1)&1，输入选 c&1。两个槽隔开当期读写；不能据此声称整个音频系统只有两块实际媒体内存。

- **图周期**：由图 Driver 发起的一轮处理。周期时长与实际采样率、处理帧数和配置有关；一个图周期不固定等于某个毫秒数。

- **同步 / 异步**：必须说明作用范围。JACK2 服务器模式讨论本周期处理与输出交付关系；PipeWire 异步 Link 讨论跨连接的周期隔离；异步控制消息仅说明请求与处理不必当场完成。三者不能互相替代。

- **I/O 区**：PipeWire/SPA 交换处理状态与缓冲标识等信息的区域。它帮助说明当前应消费或提供哪份缓冲，不能一概等同于存放所有音频样本的媒体内存。

## 第 15 页：素材参考：PipeWire 作者的整体架构图

### 这一页在讲什么

作者原图同时包含音频、视频和系统后端。SPA 是插件接口，ALSA-lib/BlueZ/libcamera 是不同设备领域的组件。该图是2024年架构快照，不是当前版本全部能力清单。

### 术语与例子

- **SPA**：Simple Plugin API，PipeWire 用于构建低层插件和节点能力的一套接口。它帮助把设备访问、格式与缓冲等机制做成可组合组件，不是会话策略管理器。

- **插件**：按约定接口扩展框架能力的模块，可以提供设备、处理或格式支持。不同系统的插件 ABI 和职责范围不同。

- **ALSA-lib**：ALSA 的用户态库，把应用可用的接口与底层音频设备能力连接起来。图里它在用户态，下面还有 Linux 内核的驱动部分。

- **BlueZ**：Linux 的蓝牙协议栈及相关组件。PipeWire 可以借助它处理蓝牙音频设备接入；BlueZ 本身不是混音引擎。

- **libcamera**：面向摄像设备的用户态相机支持框架。它出现在 PipeWire 总览里，是因为 PipeWire 覆盖视频媒体处理，不只处理声音。

- **内核**：操作系统中管理硬件、内存、进程与调度等基础能力的核心部分。声卡驱动位于这一层；上层媒体服务通过系统接口使用这些能力。

- **Node**：节点，一项处理职责的承载者，如输入、重采样、混音或输出。不同框架对 Node 的粒度和执行方式不同，不能只凭同名断定实现相同。

- **端口**：节点或客户端的数据连接端点，例如一个音频输入或输出端口。这里通常是软件音频端点，不是网线插口，也不是 TCP 端口号。

## 几个计算与判断例子

- **数据量**：48 kHz、双声道、16 位 PCM，每秒数据量是 48000×2×2＝192000 字节，约 192 kB/s（不含容器头等开销）。采样率不等于每秒字节数。

- **周期**：128 帧÷48000 帧/秒≈2.67 ms。若多个节点在同一依赖链上，它们要共同满足这轮处理时限。

- **理想并行**：A=2、B=3、C=2、D=1 个时间单位；A/B 独立后汇入 C→D。串行总和 8，两个资源理想情况下为 max(2,3)+2+1=6。它是教学下界，不是 JACK 或 PipeWire 的性能测量。

- **延迟**：增加一周期交付等待，若图周期是 2.67 ms，新增量约为 2.67 ms；总端到端延迟还要加上其它环节。不能把此数当成完整播放延迟。

- **不能混为一谈**：同步/异步描述何时交付或怎样等待；串行/并行描述工作是否同时执行；共享内存描述数据如何被访问。它们是不同维度。
